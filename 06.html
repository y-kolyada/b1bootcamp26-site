    Занятие 6 · Приёмка чужой работы

    До сих пор твоё задание выполнял твой агент, а принимал работу ты. Сегодня твоё задание выполняет напарник со своим агентом - в твоём репозитории. А ты выполняешь задание напарника в его репозитории. Каждый побывает и хозяином, и исполнителем.

    Главная мысль занятия #

    Принимают по предикатам, а не по вкусу. Тебе может не понравиться цвет кнопки, которую сделал напарник. Но если в твоём задании про цвет ничего не было, это не повод для возврата. Это повод в следующий раз написать задание точнее.

    Нет требований - нет приёмки. Это правило 5 курса. Сегодня ты впервые применяешь его не к ИИ, а к живому человеку. Так тренер каждый день принимает работу ИИ.

    1 · Цель занятия #

    Один раз поставить задание другому человеку и принять его работу. И один раз выполнить чужое задание. У тебя две роли:

    • хозяин - пишет задание для напарника, приглашает его в свой репозиторий, принимает работу или возвращает её;
    • исполнитель - делает задание хозяина в его репозитории, в своей ветке, и присылает работу на приёмку.

    Два новых слова этого занятия:

    • Ветка - отдельная линия работы в репозитории. Исполнитель работает в своей ветке, а главная ветка хозяина - main - остаётся нетронутой, пока хозяин не примет работу.
    • Пул-реквест (pull request) - просьба «влей мою ветку в свою main». На его странице на GitHub хозяин видит работу и нажимает кнопку, если принимает. А своё решение - принять или вернуть - хозяин записывает в zapis-6.md.

    Кто кому делает работу #

    Группа делится на пары. Если людей нечётное число, одна тройка встаёт по кругу. Например, так. Стрелка значит: «приглашает к себе и принимает работу».

    Пара 1:   А → Б   и   Б → А
Пара 2:   В → Г   и   Г → В
Тройка:   Д → Е,  Е → Ж,  Ж → Д

    В паре вы делаете задания друг другу. В тройке - по кругу: Д принимает работу Е, Е принимает работу Ж, Ж принимает работу Д. Каждый ровно один раз хозяин и ровно один раз исполнитель. Никто не принимает свою работу. Кто в какой паре, говорит тренер.

    Одно правило для исполнителя #

    В чужом репозитории ты работаешь только в своей ветке и ничего не пишешь в main. Приглашение даёт тебе право менять в репозитории хозяина всё. Но main - его, и туда работа попадает только через пул-реквест, когда хозяин её принял.

    Четыре промпта этого занятия #

    Промпты универсальные: работают на любом сайте. Копируй и отдавай своему агенту.

    1. «Сделай задание хозяина» - для исполнителя.
    2. «Помоги мне принять работу» - для хозяина.
    3. «Запиши моё решение» - для хозяина: принимаю или возвращаю.
    4. «Исправь по возврату» - для исполнителя, которому вернули.

    2 · Путь-минимум: мышкой, без терминала #

    Шаги идут по порядку, но делают их разные люди. Над каждым шагом написано, чей он: хозяина или исполнителя.

    1 Хозяин: задание для напарника #

    Сделай себе шестую пару артефактов: zadanie-6.md и zapis-6.md. В задании 6 опиши одну маленькую вещь для своего сайта и три предиката к ней.

    Это задание будет читать человек, который видит твой сайт впервые. Он не знает, что ты имел в виду. Поэтому в каждом предикате назови файл, кнопку или текст, которые можно найти. Как это выглядит - в образцах ниже.

    В zapis-6.md пока только заголовок «Запись 6»: в него вы с напарником будете дописывать всю историю работы.

    Оба файла должны лежать на GitHub до приглашения - чтобы напарник получил файл, а не устное «сделай что-нибудь». В редакторе: вкладка Source Control → сообщение docs: задание 6 для напарника → Commit → Sync Changes.

    После шага существует: zadanie-6.md с тремя предикатами, понятными чужому человеку, и пустая zapis-6.md - на GitHub, в main.
    2 Хозяин: пригласи напарника #

    На GitHub открой свой репозиторий и пригласи напарника:

    1. Settings → Collaborators (GitHub может попросить пароль - это нормально).
    2. Add people → впиши ник напарника на GitHub → выбери его → Add to repository.
    Должно получиться: ник напарника в списке с пометкой Pending invite - приглашение ждёт, пока он его примет.

    Скажи напарнику адрес своего репозитория и правило про main.

    После шага существует: приглашение, которое ждёт напарника.
    3 Исполнитель: прими приглашение и забери репозиторий #

    Открой в браузере адрес репозитория хозяина и допиши в конце /invitations:

    https://github.com/ник-хозяина/его-репозиторий/invitations

    Нажми Accept invitation. Теперь забери репозиторий к себе. В редакторе открой новое окно и:

    1. Ctrl+Shift+P → Git: Clone;
    2. вставь адрес https://github.com/ник-хозяина/его-репозиторий;
    3. выбери папку и нажми Open.
    Должно получиться: окно редактора с файлами хозяина, и среди них его zadanie-6.md.
    После шага существует: копия репозитория хозяина у тебя на компьютере, в отдельной папке. Твой собственный репозиторий не тронут.
    4 Исполнитель: промпт «Сделай задание хозяина» #

    Открой Claude Code в окне с репозиторием хозяина и отдай ему этот промпт. В строке про ветку поставь свой ник латиницей:

    Это не мой репозиторий. Я исполнитель, а принимает работу хозяин репозитория.
Прочитай zadanie-6.md - это задание хозяина для меня.
1. Создай ветку zadanie-6-мой-ник и работай только в ней. В main ничего не пиши.
2. Сделай задание. Ничего сверх задания не меняй, даже если тебе кажется, что так лучше.
3. Запусти ./check.sh хозяина и покажи последнюю строку.
4. Отправь ветку на GitHub и открой пул-реквест в main.
   В описании пул-реквеста - по каждому предикату: ДА или НЕТ, и где это посмотреть.
Команды, которые нужно выполнить мне самому, выпиши отдельным списком.
    Должно получиться: адрес пул-реквеста вида https://github.com/ник-хозяина/его-репозиторий/pull/1.

    Отправь этот адрес хозяину. Пункт 2 промпта - самый важный: сделать больше, чем просили, - тоже ошибка. Хозяин принимает по своим предикатам, и лишнее ему придётся проверять, не прося об этом.

    После шага существует: пул-реквест в репозитории хозяина, в описании которого твой отчёт по каждому его предикату.
    5 Хозяин: промпт «Помоги мне принять работу» #

    Отчёт исполнителя в пул-реквесте - это его слова, а не доказательство. Как и слова ИИ на занятии 3. Открой Claude Code в своём репозитории:

    Напарник прислал пул-реквест в мой репозиторий. Я хозяин, и решаю я.
1. Найди открытый пул-реквест и переключи меня на его ветку.
2. Пройди по каждому предикату моего zadanie-6.md: ДА или НЕТ, и чем это проверено.
3. Запусти ./check.sh и покажи последнюю строку.
4. Ничего не исправляй и ничего не добавляй от себя. Твоё дело - доложить.
5. Скажи, как мне открыть страницу из этой ветки в браузере, чтобы я посмотрел сам.
    Должно получиться: три строки ДА или НЕТ по твоим предикатам и последняя строка проверки.

    Теперь открой страницу в браузере и посмотри сам. Отчёт агента - тоже слова. Твоё решение - по тому, что ты увидел.

    После шага существует: твой ответ ДА или НЕТ по каждому предикату, проверенный своими глазами.
    6 Хозяин: решение - принять или вернуть #

    Все три ДА - принимаешь. Хоть одно НЕТ - возвращаешь. Решение записывается в zapis-6.md: там живёт вся история работы, а не в комментариях на GitHub. Запись набирает агент, ты проверяешь. Впиши в первую строку своё решение:

    Моё решение: возвращаю по предикату 2: ожидал ..., вижу ...
(или: принимаю, предикаты 1, 2 и 3 - ДА)
1. Мы на ветке пул-реквеста. Забери её свежую версию с GitHub.
2. Допиши в конец zapis-6.md раздел «Приёмка N · хозяин», где N - следующий номер.
   В нём моё решение: при возврате - одна строка на каждый невыполненный предикат,
   в виде «Возвращаю по предикату N: ожидал ..., вижу ...»; при приёмке - одна строка «Принимаю: ...».
   Ничего не добавляй от себя: ни похвалы, ни советов, ни своего вкуса.
3. Покажи мне раздел, прежде чем сохранять. Потом сохрани коммитом и отправь ветку на GitHub.
4. Напиши в пул-реквест одну строку: «Возвращаю, причины в zapis-6.md» или «Принимаю, запись в zapis-6.md».
    Должно получиться: новый раздел в конце zapis-6.md и одна строка в пул-реквесте на GitHub.

    Принимаешь - на странице пул-реквеста на GitHub нажми Merge pull request → Confirm merge. Вся история из zapis-6.md вместе с работой попадает в твой main.

    Возврат без номера предиката - это не возврат, а вкус. «Мне не нравится цвет» - вкус. «Возвращаю по предикату 2: ожидал кнопку „Начать заново", вижу, что её нет» - возврат. Если хочется вернуть, а предиката под это нет, - значит, задание было неполным. Прими работу, а в следующем задании допиши предикат.

    После шага существует: твоё решение в zapis-6.md с номерами предикатов, строка о нём в пул-реквесте, а при приёмке - влитая работа.
    7 Исполнитель: промпт «Исправь по возврату» #

    Этот шаг - только если тебе вернули работу. Приняли - иди на шаг 8. Возврат - не обида и не провал: это обычная работа. В окне с репозиторием хозяина:

    Хозяин вернул работу. Возврат записан в zapis-6.md в моей ветке.
1. Забери свежую версию моей ветки с GitHub: хозяин дописал туда запись.
2. Прочитай последний раздел «Приёмка · хозяин» в zapis-6.md.
3. Исправь ровно то, по чему вернули. Больше ничего не меняй.
4. Допиши в конец zapis-6.md раздел «Исправление N · исполнитель 1»:
   одна строка на каждый предикат из возврата - что исправлено.
5. Запусти ./check.sh, сохрани коммитом и отправь ветку на GitHub.
6. Напиши в пул-реквест одну строку: «Исправлено, запись в zapis-6.md».
    Должно получиться: исправление и новый раздел в zapis-6.md в том же пул-реквесте, и одна строка на GitHub.

    Сначала - свежая версия. Пункт 1 нельзя пропускать: хозяин дописал в файл свой раздел. Кто пишет в zapis-6.md, тот сначала забирает свежую версию, а потом дописывает - иначе две записи столкнутся.

    Скажи хозяину, что исправил. Он снова идёт на шаги 5 и 6.

    После шага существует: исправленная работа в том же пул-реквесте.
    8 Хозяин: убери напарника и запиши, что было #

    Приглашение было временным. На GitHub: Settings → Collaborators → напротив ника напарника Remove.

    Забери к себе принятую работу. В редакторе: внизу слева переключись на ветку main → Sync Changes.

    Твоя роль хозяина уже записана: приёмки и исправления пришли в zapis-6.md вместе с работой. Осталась роль исполнителя. Запись набирает агент, твоё дело - проверить, что записанное правда. Вставь адрес своего пул-реквеста у напарника:

    Допиши в конец zapis-6.md раздел «Моя работа исполнителем».
Мой пул-реквест у напарника вот здесь: адрес.
Прочитай zapis-6.md напарника в его репозитории и перенеси оттуда его решения
о моей работе - строки как есть. Добавь ссылку на его zapis-6.md.
Ничего не выдумывай. Чего не нашёл - спроси меня.
    Должно получиться: раздел «Моя работа исполнителем» в твоём zapis-6.md со ссылкой на запись напарника.

    Сверь запись с правдой: открой zapis-6.md напарника на GitHub и сравни его решения с тем, что перенёс агент. Нашёл расхождение - верни агенту и пусть исправит. Потом: Source Control → сообщение docs: запись 6 - приёмка и исполнение → Commit → Sync Changes.

    После шага существует: в твоём main - работа напарника, которую ты принял, и zapis-6.md со всей историей: твои решения хозяина, исправления исполнителя и твоя работа у напарника. Напарника в репозитории больше нет.

    Образцы: форма, а не содержание #

    Это примеры с чужих сайтов, а не с твоего. Образцы показывают, какого размера бывает задание для напарника и как писать предикаты, которые поймёт чужой человек. Твоё задание - про твой сайт. Правило 6 курса: делай как я, делай лучше меня.

    Три образца задания 6 - каждое на 20-30 минут работы:

    Викторина по истории.
Хочу: кнопку «Случайный вопрос».
1. На index.html под заголовком есть кнопка с текстом «Случайный вопрос».
2. После нажатия на неё текст вопроса на странице меняется.
3. ./check.sh остаётся ЗЕЛЁНЫМ.
    Трекер привычек.
Хочу: счётчик сделанного за сегодня.
1. Над списком привычек есть строка «Сделано сегодня: 0 из N», где N - число привычек.
2. Когда отмечаешь привычку, первое число в строке растёт на 1.
3. ./check.sh остаётся ЗЕЛЁНЫМ.
    Каталог моей коллекции.
Хочу: подпись с годом под каждой карточкой.
1. Под каждой карточкой есть строка «Год: ...».
2. Ни у одной карточки год не пустой.
3. ./check.sh остаётся ЗЕЛЁНЫМ.

    Заметь предикат 3: он у всех одинаковый. Работа напарника не должна ломать то, что у тебя уже работало, - и твоя проверка это покажет.

    Плохо → хорошо: предикат для чужого человека

    • «сделай красивее» → «у заголовка страницы другой цвет, чем у основного текста»;
    • «добавь что-нибудь интересное» → «под заголовком есть кнопка „Случайный вопрос"»;
    • «чтобы работало» → «после нажатия на кнопку текст вопроса меняется».

    Образец истории в zapis-6.md - возврат, исправление, приёмка:

    ## Приёмка 1 · хозяин
Возвращаю по предикату 2: ожидал, что после нажатия вопрос меняется, вижу, что остаётся тот же.

## Исправление 1 · исполнитель 1
Исправлено по предикату 2: кнопка теперь берёт случайный вопрос из списка.

## Приёмка 2 · хозяин
Принимаю: предикаты 1, 2 и 3 - ДА.

    В записи - роли, а не имена: хозяин, исполнитель 1, исполнитель 2. Если над сайтом работает команда, номер показывает, чья это часть работы. А кто именно сделал коммит, помнит git - у каждого коммита есть автор.

    Образец описания пул-реквеста. Его набирает агент исполнителя на шаге 4. Хозяин видит это описание на странице пул-реквеста на GitHub, без терминала:

    Сделано по zadanie-6.md.
1. ДА - кнопка «Случайный вопрос» под заголовком index.html.
2. ДА - нажми кнопку несколько раз, вопрос меняется.
3. ДА - ./check.sh: ЗЕЛЁНОЕ.

    3 · Путь-100%: в терминале через Claude Code #

    Путь настоящего инженера: правило про main держит не слово, а настройка, и приёмку ты делаешь командами.

    1 Хозяин: защита main в настройках #

    Правило «в main не пишешь» - это слово. Слово можно забыть. Настройка не забывает. На GitHub в своём репозитории:

    1. Settings → Branches → Add classic branch protection rule;
    2. Branch name pattern: main;
    3. отметь Require a pull request before merging, а в нём сними галочку Require approvals - иначе кнопка Merge будет ждать отдельного одобрения, кроме твоего комментария;
    4. Create.

    Защита, которую ни разу не испытали, ещё не защита. Попроси исполнителя попробовать отправить прямо в main пустой коммит - он не меняет ни одного файла, поэтому испытание безопасно:

    git switch main
git commit --allow-empty -m "проверка защиты main"
git push origin main
    Должно напечатать у исполнителя: отказ, в котором есть слова Protected branch. Отправка прошла - защита не работает: проверь настройку. Файлы от этого не пострадали - коммит был пустой.

    Ты сам, как хозяин, по-прежнему можешь писать в main: правило держит гостей, а не владельца.

    После шага существует: main, в который работа попадает только через пул-реквест, и отказ, который ты видел своими глазами.
    2 Хозяин: приёмка командами #

    То же, что шаги 5 и 6, но руками, без промпта. В терминале, в своём репозитории:

    gh pr list
gh pr checkout 1
./check.sh
    Должно напечатать: список пул-реквестов, переключение на ветку исполнителя и вывод твоей проверки на его работе.

    Посмотри страницу в браузере. Потом допиши своё решение в конец zapis-6.md - раздел «Приёмка N · хозяин», как на шаге 6. Сохрани его и отправь на GitHub:

    git add zapis-6.md
git commit -m "docs: приёмка - решение хозяина"
git push
    Должно напечатать: коммит и строку отправки ветки пул-реквеста на GitHub.

    И одна строка в пул-реквест. Возвращаешь - первая команда, принимаешь - вторая и третья:

    gh pr comment 1 -b "Возвращаю, причины в zapis-6.md"
    gh pr comment 1 -b "Принимаю, запись в zapis-6.md"
gh pr merge 1 --merge
    Должно напечатать: адрес нового комментария, а при приёмке - ещё и строку о том, что пул-реквест влит.

    Вернись в main и забери принятое: git switch main, потом git pull.

    После шага существует: решение в zapis-6.md, принятое командами, и принятая работа в твоём main.

    4 · Путь-максимум: продолжение следует #

    Для тех, кто хочет принимать работу так, как это делают на настоящей работе.

    1 Не сделал ли исполнитель лишнего #

    Предикаты говорят, что должно появиться. Но они молчат о том, что не должно было измениться. Посмотри, что изменил пул-реквест, своими глазами:

    gh pr diff 1
    Должно напечатать: все изменённые строки пул-реквеста: зелёные добавлены, красные убраны.

    Есть изменения, о которых задание не просило? Это тоже повод для возврата, но с причиной: «Возвращаю: изменён файл style.css, а задание его не касалось». И повод в следующем задании дописать предикат «ничего, кроме ..., не меняется».

    После шага существует: твой ответ на вопрос «не сделано ли лишнего», проверенный по изменённым строкам.
    2 Предикат или вкус: проверь своё решение #

    Самое трудное в приёмке - не путать «не по заданию» с «не по-моему». Дай агенту проверить тебя самого:

    claude "Вот моё задание zadanie-6.md и мои решения в разделах «Приёмка · хозяин» в zapis-6.md.
Пройди по каждой строке моих решений: она опирается на номер предиката из задания или это мой вкус?
Про каждую строку - одно слово: ПРЕДИКАТ или ВКУС, и почему."
    Должно получиться: по слову ПРЕДИКАТ или ВКУС на каждую строку твоих решений.

    Нашлась строка ВКУС - это не стыдно. Это подсказка: в задание надо было дописать ещё один предикат.

    После шага существует: решение, в котором ты отличил предикаты от вкуса.

    5 · Артефакты: что у тебя есть после занятия #

    Занятие >> Твой квант времени жизни · Партнёрство достоинства вместе с AI · Перестройка твоей нейросети

    Занятие - это занятая тобой часть времени твоей жизни. Сегодня ты потратил её на то, чтобы побыть по обе стороны работы: тем, кто ставит задание, и тем, кто его выполняет. Главный артефакт дня - не файл, а умение: вернуть работу человеку по предикату, без обиды и без вкуса. Твоя нейросеть научилась отличать «не по заданию» от «не по-моему».

    Материальный перечень артефактов шестого занятия:

    1. zadanie-6.md - задание для напарника, понятное чужому человеку. В main.
    2. Пул-реквест в твоём репозитории - работа напарника и строка о твоём решении.
    3. Принятое чужое изменение - работа напарника, влитая в твой main.
    4. Пул-реквест в репозитории напарника - твоя работа исполнителем.
    5. zapis-6.md - вся история работы: твои решения хозяина, исправления исполнителя и раздел о твоей работе у напарника. В main.

    Памятка: команды этого занятия

    • gh pr list - какие пул-реквесты открыты в репозитории.
    • gh pr checkout 1 - переключиться на ветку пул-реквеста номер 1.
    • gh pr comment 1 -b "..." - одна строка в пул-реквест: принимаю или возвращаю, причины в записи.
    • gh pr merge 1 --merge - влить принятую работу в main.
    • git switch main и git pull - вернуться на main и забрать принятое.
